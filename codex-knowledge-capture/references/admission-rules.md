# 知识准入规则

## 核心判断

一条信息只有同时满足以下条件，才应进入正式知识文档：

1. 对未来任务仍有帮助，而不只是描述当前进度。
2. 属于当前项目，并且适用范围可以说清楚。
3. 有用户确认、执行验证或项目材料支持。
4. 不包含秘密或不必要的个人信息。
5. 与已有知识相比，带来了新结论或有效补充。

## 优先沉淀

| 类型 | 典型内容 | 示例 |
| --- | --- | --- |
| `decision` | 已确认的技术或产品选择 | “服务端时间统一存 UTC” |
| `constraint` | 必须遵守的项目限制 | “该模块不得访问公网” |
| `validated-solution` | 已验证有效的解决方案 | “启用批量查询后消除了 N+1 请求” |
| `pitfall` | 可复用的失败模式与规避方式 | “只改生成文件会被下次代码生成覆盖” |
| `project-fact` | 隐蔽但稳定的项目事实 | “协议源文件位于另一个仓库” |
| `project-preference` | 用户明确提出的本项目习惯 | “本项目的设计文档统一放在 docs/design” |

## 不要沉淀

- “正在修改”“测试还在运行”等临时状态。
- 没有得到验证的原因猜测。
- 可以通过打开单个显眼文件立即获得的信息。
- 大段聊天原文、完整终端日志或完整代码复制。
- 密码、Cookie、Token、私钥、内部凭据和个人敏感信息。
- 与当前项目无关的通用常识。
- 仅仅因为出现过一次、但尚不能复用的偶发现象。

## 证据规则

正式条目允许：

- `user-confirmed`：用户明确指定、选择或确认。
- `verified`：测试、构建、运行结果或可复现步骤直接证明。
- `observed`：代码、配置、正式文档或稳定项目结构直接证明。

`inferred` 表示合理推断，但不足以形成正式结论。它只能使用 `conflict` 动作进入待确认区。

## 去重与冲突

先按稳定 ID 搜索，再按标题、关键词和结论搜索。

- 措辞不同但含义相同：视为同一条目。
- 新信息只增加原因、范围或证据：更新原条目。
- 新旧结论互相排斥：记录冲突，保留原条目。
- 旧结论明确过时：获得用户确认或直接验证后更新，并记录变更依据。

## 内容粒度

一条知识只表达一个中心结论。标题说明主题，结论说明应记住什么，原因说明为什么，细节只保留未来执行需要的信息。

不要把整次任务总结塞进一个条目；按独立、可更新的知识点拆分。

## 表达准入

内容正确但表达不合格时，也不得写入。写入前必须满足：

- 已从对话措辞中抽离，表达的是实际含义，不是原句的直译或改写。
- 使用项目语境下含义明确的术语，避免“这个东西”“做一下适配”“相关处理”等空泛表述。
- 先给结论，再给必要的关键点和依据。
- 删除不影响未来决策的讨论过程、情绪、客套和重复说明。
- 框架、流程或多节点关系已有合适的 Mermaid，或明确说明不适合画图的原因。
- 数学公式采用 Markdown 可渲染的 LaTeX 定界符：行内使用 `$...$`，独立公式使用 `$$...$$` 块。
