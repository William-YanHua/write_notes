# 文档类型整理风格

本规范用于把用户交互、代码事实、数据和验证结果整理成正式文档，不用于从零补齐用户没有提供的方案、数据或结论。缺失但会影响结论的信息应保留为明确的未决项，不得用通用模板虚构内容。

文档类型决定材料的取舍、详略和叙述顺序；`writing_style` 决定同一内容面向不同读者时的术语密度和解释深度。两者同时生效。下面的“成文主线”只表示逻辑顺序，不得直接复制成章节标题。

## 通用整理规则

- 只将用户确认、项目材料直接支持或执行结果已经验证的内容写成确定事实。推断必须明确标注，冲突信息进入待确认流程。
- 沿用用户已经使用且含义明确的术语，不随意更换同义词或创造新术语。
- 必须使用用户未曾提及的术语时，在首次出现处用当前场景下的通俗语言说明具体含义；缩写首次出现时写出全称。后文保持同一含义。
- 术语说明只写理解当前内容所需的信息，不扩展成百科式定义。能用普通语言准确表达时，不额外引入专业术语。
- 删除对话顺序、修改过程、评审话术和重复表达，将多轮交互中的同一结论合并到最合适的位置。
- 一份文档只选择一个主要类型。其他类型的内容只在支撑主线时保留，不拼接多套固定栏目。

术语说明示例：

> 系统采用熔断机制。熔断是指下游连续失败达到阈值后，暂时停止调用，避免故障继续扩大。

## 方案型 `proposal`

- **成文主线**：目标和约束 → 总体做法 → 分步做法 → 关键规则 → 风险与落地条件。
- **重点保留**：用户已经确认的目标、选定方案、执行动作、责任边界、依赖、时间要求和验收口径。
- **压缩删除**：讨论过程、常识性背景、已经否决且不影响理解的选项，以及“为什么要写这份方案”等元话语。
- **语言要求**：直接写“做什么、怎么做、做到什么程度”，多用明确动词和确定条件。除必要的术语定义，以及会影响执行或取舍的原因外，不展开解释性语言。

## 分析型 `analysis`

- **成文主线**：结论 → 数据事实 → 分层推导 → 原因判断 → 建议或未决问题。
- **重点保留**：统计口径、时间范围、基线、对照组、关键数据、异常值、证据强度和推理链。
- **压缩删除**：没有数据支持的直觉、与结论无关的数据堆叠、重复图表描述和无法验证的因果判断。
- **语言要求**：每个判断紧跟依据，区分事实、相关性、因果性和推断；结论强度不得超过数据强度。数据不足时直接说明不能得出什么结论。

## 需求型 `requirements`

- **成文主线**：用户与场景 → 当前问题 → 目标结果 → 功能和规则 → 边界与验收。
- **重点保留**：用户在交互中确认的角色、触发场景、期望行为、优先级、范围、非目标、异常分支和可验证标准。
- **压缩删除**：实现方案争论、没有形成需求的想法、重复的背景叙述和无法验收的口号。
- **语言要求**：使用可观察行为描述需求，明确谁在什么条件下执行什么动作并得到什么结果；避免“优化体验”“支持相关能力”等模糊表达。

## 架构说明 `architecture`

- **成文主线**：系统目标 → 整体结构 → 组件关系 → 关键链路 → 边界与演进。
- **重点保留**：已确认的系统边界、组件职责、数据或调用方向、依赖关系、关键约束和架构取舍。
- **压缩删除**：逐文件介绍、低层实现流水账、与整体关系无关的局部细节和讨论历史。
- **语言要求**：先写关系再写组件细节；图表达结构，正文只补充图中看不出的职责、约束和因果。

## 技术设计 `technical-design`

- **成文主线**：要解决的技术问题 → 约束 → 选定设计 → 关键机制 → 上下游影响 → 验证与发布。
- **重点保留**：接口和数据结构、核心流程、异常处理、兼容性、性能容量、备选方案中影响选择的差异，以及已经确认的测试和回滚设计。
- **压缩删除**：与最终设计无关的探索过程、已被取代的代码细节、不能影响实现的泛化背景。
- **语言要求**：机制和边界详细，背景简短；说明设计为何成立及代价，但不写教程式解释。用户未确认的实现细节不得自行补成确定方案。

## 项目指南 `project-guide`

- **成文主线**：项目定位 → 核心模型 → 模块关系 → 常见工作路径 → 约束和验证入口。
- **重点保留**：交互中稳定形成的项目认知、关键目录或模块、推荐工作方式、常见任务入口和容易误用的规则。
- **压缩删除**：单次任务过程、短期进度、可从目录直接看出的文件罗列和已经失效的操作习惯。
- **语言要求**：面向新进入项目的读者，从整体到局部；只解释完成常见判断和操作所需的概念。

## 操作手册 `operation-manual`

- **成文主线**：适用场景与前提 → 操作顺序 → 每步可观察结果 → 异常分支 → 完成确认。
- **重点保留**：用户实际执行过或验证过的入口、参数、顺序、判断条件、权限和恢复方法。
- **压缩删除**：设计原理、讨论过程、与操作无关的背景，以及未经验证的命令和结果。
- **语言要求**：使用命令式短句，一步只写一个动作；输入、操作和预期结果紧邻呈现，危险或不可逆动作明确标出。

## 接口文档 `api-reference`

- **成文主线**：接口用途和边界 → 调用约束 → 请求 → 响应 → 错误与调用语义 → 示例。
- **重点保留**：已确认的协议、鉴权、字段含义、必填性、类型、状态码、错误码、幂等、超时、重试、限流和兼容规则。
- **压缩删除**：接口设计讨论、字段命名争论、与调用者无关的内部实现，以及不能代表真实行为的示例。
- **语言要求**：字段描述短而无歧义，约束写成确定条件；示例必须与字段定义一致，并优先覆盖正常、失败和边界场景。

## 排障文档 `troubleshooting`

- **成文主线**：可观察现象 → 快速分流 → 逐步诊断 → 根因对应处理 → 恢复验证与升级条件。
- **重点保留**：真实现象、日志或指标证据、诊断判断点、已验证根因、有效修复和排除过的相似问题。
- **压缩删除**：完整聊天排查过程、无效尝试的流水账和不能复用的临时环境细节；只有能避免误判时才保留失败尝试。
- **语言要求**：每一步同时说明“看什么”和“结果意味着什么”，使读者能沿证据分支定位问题，而不是照抄命令清单。

## 故障复盘 `postmortem`

- **成文主线**：结论与影响 → 关键时间线 → 直接原因 → 根本原因和促成因素 → 处置效果 → 改进项。
- **重点保留**：经过确认的时间、影响数据、证据链、恢复动作、决策节点、系统性原因和有负责人及期限的行动项。
- **压缩删除**：群聊逐句记录、重复时间点、情绪化评价、责任归咎和没有证据的原因猜测。
- **语言要求**：事实与分析分开，时间线简洁，原因分析详细，结论克制；用系统条件解释事故，不用个人失误替代根因。

## 决策记录 `decision-record`

- **成文主线**：决策上下文 → 约束 → 被比较的选项 → 最终决定 → 关键理由与代价 → 重评条件。
- **重点保留**：真正影响决策的事实、各方案在统一维度上的差异、明确决定、承担的后果和适用边界。
- **压缩删除**：没有进入实质比较的想法、冗长会议过程、重复观点和不影响选择的细节。
- **语言要求**：决定先行，理由围绕选择标准展开；不把最终方案写成没有代价的唯一正确答案。

## 测试报告 `test-report`

- **成文主线**：测试结论 → 对象与口径 → 结果数据 → 失败和阻塞分析 → 发布判断。
- **重点保留**：版本和环境、覆盖范围、通过标准、通过率、失败数、与基线差异、问题证据和复现条件。
- **压缩删除**：正常用例的逐条流水账、无关日志、没有改变结论的执行细节和未经复核的失败归因。
- **语言要求**：先明确是否满足目标，再用数据支撑；失败项写清预期、实际、影响和证据，结论不得把“未测试”写成“已通过”。

## 调研对比 `comparative-research`

- **成文主线**：调研结论 → 比较前提 → 统一维度 → 关键差异 → 推荐及适用条件。
- **重点保留**：用户关心的约束、可靠来源、统一口径下的事实、各选项优缺点和能够改变选择的差异。
- **压缩删除**：产品宣传语、不同口径数据的直接比较、与决策无关的功能罗列和为支持结论而选择性保留的证据。
- **语言要求**：先给推荐，再给对比依据；事实与评价分开，相同维度使用平行句式，明确推荐成立的条件和不适用场景。

## 研究笔记 `research-note`

- **成文主线**：研究问题 → 核心结论 → 新见解 → 方法 → 证据 → 限制与可迁移启示。
- **重点保留**：材料中的问题定义、关键机制、实验证据、作者结论、阅读者的独立判断和仍未验证的推断。
- **压缩删除**：与核心问题无关的背景、论文或资料的章节复述，以及没有形成认识的摘抄。
- **语言要求**：背景和结论简洁，新见解、方法与证据详细；明确区分资料原文结论和整理者推断。

## 论文阅读 `paper-reading`

- **成文主线**：论文解决的问题 → 核心创新 → 方法流程 → 实验如何验证 → 结论、局限和启示。
- **重点保留**：创新相对已有工作的差异、模型或算法细节、训练与推理流程、实验设置、关键数据、消融结果和适用条件。
- **压缩删除**：大段领域史、逐章节摘要、与创新无关的公式推导和作者没有证明的延伸结论。
- **语言要求**：背景简洁，创新点和方案详细，实验围绕“是否证明主张”展开，结论简洁；公式后紧跟变量含义和它在方法中的作用。

## 进展汇报 `progress-report`

- **成文主线**：当前结论 → 已完成结果 → 进行中事项 → 风险和偏差 → 下一步及所需支持。
- **重点保留**：相对目标的结果、量化进度、关键产出、计划偏差、阻塞原因、责任人和新的时间预期。
- **压缩删除**：不能体现结果的过程罗列、每日操作流水、重复状态和已经关闭且不影响当前判断的问题。
- **语言要求**：结果优先，短句表达；风险同时写影响和处理状态，需要决策或协助的事项单独明确提出。

## 会议纪要 `meeting-notes`

- **成文主线**：会议目标 → 已达成结论 → 关键分歧或未决项 → 行动项。
- **重点保留**：明确决定、决定成立的条件、仍影响后续的不同意见，以及行动项的负责人、交付物和期限。
- **压缩删除**：逐人发言、寒暄、重复观点、没有形成结论的即时表达和与会议目标无关的话题。
- **语言要求**：按议题合并多人表达，不按发言顺序记流水账；未达成一致的内容明确写为未决，不得润色成会议结论。

## 总结型 `summary`

- **成文主线**：总体结论 → 目标与结果对照 → 关键成果 → 问题和经验 → 后续动作。
- **重点保留**：能够证明结果的事实和数据、关键转折、可复用经验、未解决问题及其后续安排。
- **压缩删除**：工作事项清单、过程细节、重复成绩描述、没有证据的价值拔高和无法转化为行动的感想。
- **语言要求**：结论简洁，结果用对比表达，经验写成可迁移的条件和做法；问题不回避，也不展开成复盘式长篇分析。

## 混合类型处理

一份文档只选择一个主要类型。交互内容同时包含多种用途时，按读者最终要完成的动作选择主要类型，再吸收辅助类型的必要规则：

- 技术方案中包含测试结果，仍以“如何实现”为主线，测试数据只用于证明设计可行。
- 分析报告中包含建议，仍以证据和推导为主线，建议必须由前文结论推出。
- 会议讨论形成正式决策时，项目主文档吸收有效决定；只有需要保留会议责任项时才另写会议纪要。

不要把多个类型的固定栏目串联起来，也不要用“背景、方案、风险、总结”覆盖所有文档。
