## 文档与日志的边界

正式文档不是日志卡片的展示层。日志回答“这次确认或改变了什么”，文档回答“一个不了解讨论过程的人，怎样系统理解并正确使用这套知识”。

项目还没有正式文档，并且满足下列条件时，才创建项目主文档：

1. 有清晰、稳定的中心主题。
2. 已知目标读者以及他们阅读后需要做出的判断或行动。
3. 材料足以形成至少三个有实质内容的章节。
4. 核心事实有用户确认、执行验证或项目材料支持。
5. 内容在未来仍有持续阅读价值，而不只是记录一次变化。

材料不足时继续积累日志。不要用重复要点、空泛背景或占位标题伪造完整性。

## 复用与拆分规则

### 默认复用项目主文档

第一份正式文档就是项目主文档。后续需求无论来自新功能、新任务、新阶段、新主题还是新的讨论日期，都先更新这份文档：在主文档内新增或重组章节，并同步修正概览、关系、边界、示例和验证信息。文档 ID 和路径保持稳定，标题只在项目定位确实改变时调整。

写作前必须先查看 `INDEX.md` 和 `documents/`。如果已有正式文档，不能通过换一个相近 ID 绕过更新，也不能把“这次内容可以单独讲清楚”当成拆分依据。

### 何时才拆分

只有同时满足以下基础条件，才考虑从项目主文档拆出新文档：

1. 内容已经形成稳定、可独立命名的边界，而不是一次任务或某个功能的临时范围。
2. 内容需要长期独立维护、独立阅读或独立评审。
3. 继续放在主文档中，即使经过删重、重组和建立目录，仍会明显损害主文档的可导航性或责任边界。
4. 拆分后两份文档的职责能够用一句话分别说明，且不会重复维护同一组核心事实。

常见的合理拆分信号包括：内容拥有不同的维护者或发布节奏；面向明显不同的读者并需要独立交付；属于需长期独立保存的事故复盘、研究报告或规范；主文档经过结构优化后仍过大，关键路径难以定位。

以下情况本身都不足以拆分：出现新主题、新模块、新功能、新任务、新里程碑、新版本、新日期，或正文已经比较长。应先尝试合并重复内容、重组章节、增加目录或压缩低价值细节。

### 拆分后的责任

拆分文档必须记录 `split_from` 和 `split_reason`，并直接从项目主文档拆出，不允许从拆分文档继续形成多层文档树。主文档保留该主题的必要概览、适用边界和链接，使读者仍能从一个入口理解项目全貌；拆分文档只承载需要独立维护的细节。两边不得复制同一段正文，跨文档共享事实时确定一个权威落点并由另一边引用。

## 写作流程

### 1. 定义文档契约

写正文前先明确：

- **主题**：整篇文章只解决哪个核心问题。
- **目标读者**：谁会读，默认具备什么知识。
- **阅读目标**：读完后应理解、判断或执行什么。
- **范围**：覆盖哪些组件、阶段或场景。
- **非目标**：哪些相关内容明确不在本文展开。
- **状态**：信息是否足够形成稳定版本。
- **落点**：本次内容应更新项目主文档的哪些章节；如果考虑拆分，四项基础条件是否全部成立。

这些内容用于规划全文，不要求机械地全部写成元数据章节。

### 2. 建立事实清单

从日志卡片、项目文件、测试结果和正式资料提取：

- 已确认事实和强约束
- 目标及其原因
- 组件、流程和依赖关系
- 方案细节与关键机制
- 方案取舍和未采用方案
- 适用范围、异常和限制
- 验证方法及结果
- 尚未解决的问题

为事实记录来源。发现冲突时停止把该结论写成确定事实，先进入待确认流程。

### 3. 先规划主线，再撰写正文

大纲应形成因果或理解顺序，而不是照时间排列讨论过程。常用主线为：

```mermaid
flowchart LR
    A[为什么需要] --> B[要解决什么]
    B --> C[整体怎么做]
    C --> D[关键部分如何工作]
    D --> E[为什么这样选择]
    E --> F[何时适用及如何验证]
```

先为每一节写一句“本节要回答的问题”。如果相邻章节回答同一个问题，应合并；如果某节没有明确问题，应删除或重新定位。

### 4. 整篇综合写作

- 开头尽快建立问题、目标和核心结论，不复述产生文档的聊天过程。
- 使用自然段解释因果、机制和取舍；列表只用于并列项、步骤或检查项。
- 让章节之间有承接关系，使读者知道为什么接下来要讨论该部分。
- 相同事实只在最合适的位置完整说明，其他章节通过引用或简短回指连接。
- 关系复杂时使用 Mermaid；数学关系使用 LaTeX。图应表达结构，文字应解释图中不明显的约束与结论。
- 来源集中放在文末“参考依据”，正文仅在证据边界会影响理解时说明来源类型。

### 5. 从读者视角复核

暂时忽略原始对话，只阅读成文结果并检查：

- 读者是否知道问题为何存在？
- 核心概念是否在首次出现时得到定义？
- 方案能否从整体进入细节，而不是突然罗列组件？
- 每个关键决定是否说明了原因和代价？
- 是否能判断方案适用于哪里、不适用于哪里？
- 是否给出了足以建立可信度的验证或依据？

## 文档类型

以下结构是内容检查清单，不是必须逐字使用的固定标题。

### 架构说明 `architecture`

至少覆盖：背景与目标、整体架构、组件职责、关键数据或调用流、设计取舍、边界与故障场景、验证和演进方向。

### 技术方案 `technical-design`

至少覆盖：问题定义、目标与非目标、约束、候选方案比较、选定方案、详细设计、兼容性与上下游影响、测试和发布计划、风险与回滚。

### 项目指南 `project-guide`

至少覆盖：适用对象、核心模型、目录或模块、关键工作方式、常见任务、约束和陷阱、验证方式、进一步阅读。

### 排障文档 `troubleshooting`

至少覆盖：现象与影响、快速判定、系统链路、诊断步骤及每步判断依据、常见根因、修复与验证、何时升级处理。

### 事故复盘 `postmortem`

至少覆盖：摘要、影响、时间线、根因、促成因素、处置过程、做得好与不足、改进项和验证方式。区分事实、推断和行动项。

### 决策记录 `decision-record`

至少覆盖：上下文、决策目标、约束、候选方案、最终决定、理由、后果、适用边界和重新评估条件。

### 研究笔记 `research-note`

至少覆盖：问题与背景、核心结论、创新点或新见解、方法或方案细节、证据和结果、限制、可迁移启示。背景与结论保持简洁，创新点和方案展开说明。

## 正文组织原则

### 完整不等于冗长

完整表示支撑理解和决策所需的信息闭环，不表示覆盖所有相关知识。每一段至少承担一种作用：定义问题、陈述结论、解释机制、提供证据、说明边界或连接上下文。

### 结论与论证配对

重要结论后应给出必要的机制、依据或取舍。避免只写“应当如此”，也避免先堆大量背景直到末尾才出现结论。

### 显式描述边界

至少说明适用范围、已知限制和例外。草稿中的未知信息应清楚标出；稳定文档不得保留占位内容。

### 控制元数据干扰

文档正文不重复展示每张日志的类型、证据等级和记录时间。日志 ID 保存在文档元数据中，来源集中放在文末。

## 更新规则

更新正式文档不是在末尾追加“最新进展”。执行以下步骤：

1. 阅读全文和现有元数据。
2. 确定新事实影响哪些结论、章节、图示、示例和边界。
3. 更新事实已经改变的段落，删除失效或重复内容。
4. 重新检查章节顺序和过渡，必要时重组大纲。
5. 同步核查上下游描述能否继续成立。
6. 更新来源、关联日志 ID、摘要和日期。
7. 重新执行完整性检查；达不到稳定标准时将状态降为 `draft`。

文档保留当前有效认知，日志保留历史演进；不要在正文内维护重复的变更流水。

## 完整性检查

写入前逐项确认：

- [ ] 标题准确命名主题，摘要能独立说明文章价值。
- [ ] 目标读者、问题、目标和范围清楚。
- [ ] 核心结论在前部出现。
- [ ] 整体结构和关键机制得到充分解释。
- [ ] 关键选择包含理由、代价或候选方案比较。
- [ ] 边界、异常、限制和上下游影响没有遗漏。
- [ ] 示例、验证或证据足以支撑主要结论。
- [ ] 章节之间是逻辑递进，不是时间流水账。
- [ ] 列表没有代替本应展开的论证。
- [ ] 图、公式、正文和来源互不重复，各自承担清晰作用。
- [ ] `stable` 文档没有占位内容或伪装成事实的推断。
- [ ] 即使看不到原始对话，文章仍可独立理解。
- [ ] 项目已有主文档时，本次内容已优先合入主文档；若拆分，四项基础条件全部满足并记录了来源与理由。

## 常见失败模式

- 按对话发生顺序写“先做了什么，后来又做了什么”。
- 每张日志变成一个章节，重复“结论、依据、适用范围”。
- 只有标题和列表，没有解释机制、取舍和边界。
- 为追求完整加入与主题无关的百科背景。
- 新信息只追加到末尾，导致正文前后矛盾。
- 按功能、任务、阶段或日期不断创建新文档，导致项目事实散落和重复维护。
- 只因为文章较长就拆分，没有先删重、重组章节和改善导航。
- 拆分后主文档没有保留概览与入口，或主文档和拆分文档重复保存同一事实。
- 把推断润色成确定事实，或让文章语气强于实际证据。
- 正文反复展示时间、ID、证据标签，破坏连续阅读。
