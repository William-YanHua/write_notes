## 文档与日志的边界

正式文档不是日志卡片的展示层。日志回答“这次确认或改变了什么”，文档回答“一个不了解讨论过程的人，怎样系统理解并正确使用这套知识”。

项目还没有正式文档，并且满足下列条件时，才创建项目主文档：

1. 有清晰、稳定的中心主题。
2. 已知目标读者以及他们阅读后需要做出的判断或行动。
3. 材料足以形成至少三个有实质内容的章节。
4. 核心事实有用户确认、执行验证或项目材料支持。
5. 内容在未来仍有持续阅读价值，而不只是记录一次变化。

材料不足时继续积累日志。不要用重复要点、空泛背景或占位标题伪造完整性。

## 复用与拆分规则

### 默认复用项目主文档

第一份正式文档就是项目主文档。后续需求无论来自新功能、新任务、新阶段、新主题还是新的讨论日期，都先更新这份文档：在主文档内新增或重组章节，并同步修正概览、关系、边界、示例和验证信息。文档 ID 和路径保持稳定，标题只在项目定位确实改变时调整。

写作前必须先查看 `INDEX.md` 和 `documents/`。如果已有正式文档，不能通过换一个相近 ID 绕过更新，也不能把“这次内容可以单独讲清楚”当成拆分依据。

### 何时才拆分

只有同时满足以下基础条件，才考虑从项目主文档拆出新文档：

1. 内容已经形成稳定、可独立命名的边界，而不是一次任务或某个功能的临时范围。
2. 内容需要长期独立维护、独立阅读或独立评审。
3. 继续放在主文档中，即使经过删重、重组和建立目录，仍会明显损害主文档的可导航性或责任边界。
4. 拆分后两份文档的职责能够用一句话分别说明，且不会重复维护同一组核心事实。

常见的合理拆分信号包括：内容拥有不同的维护者或发布节奏；面向明显不同的读者并需要独立交付；属于需长期独立保存的事故复盘、研究报告或规范；主文档经过结构优化后仍过大，关键路径难以定位。

以下情况本身都不足以拆分：出现新主题、新模块、新功能、新任务、新里程碑、新版本、新日期，或正文已经比较长。应先尝试合并重复内容、重组章节、增加目录或压缩低价值细节。

### 拆分后的责任

拆分文档必须记录 `split_from` 和 `split_reason`，并直接从项目主文档拆出，不允许从拆分文档继续形成多层文档树。主文档保留该主题的必要概览、适用边界和链接，使读者仍能从一个入口理解项目全貌；拆分文档只承载需要独立维护的细节。两边不得复制同一段正文，跨文档共享事实时确定一个权威落点并由另一边引用。

## 写作流程

### 1. 定义文档契约

写正文前先明确：

- **主题**：整篇文章只解决哪个核心问题。
- **目标读者**：谁会读，默认具备什么知识。
- **阅读目标**：读完后应理解、判断或执行什么。
- **范围**：覆盖哪些组件、阶段或场景。
- **非目标**：哪些相关内容明确不在本文展开。
- **状态**：信息是否足够形成稳定版本。
- **写作风格**：用户希望采用的表达方式；未指定时根据读者和用途选择。
- **落点**：本次内容应更新项目主文档的哪些章节；如果考虑拆分，四项基础条件是否全部成立。

这些内容用于规划全文，不要求机械地全部写成元数据章节。

### 2. 确定整理风格并建立事实清单

先选择一个主要文档类型，并完整读取 [document-type-styles.md](document-type-styles.md) 中对应的整理风格。文档类型决定从交互材料中保留什么、压缩什么以及如何排列；`writing_style` 决定这些内容如何面向目标读者表达。不得把类型说明中的检查项机械转成章节标题。

从日志卡片、项目文件、测试结果和正式资料提取：

- 已确认事实和强约束
- 目标及其原因
- 组件、流程和依赖关系
- 方案细节与关键机制
- 方案取舍和未采用方案
- 适用范围、异常和限制
- 验证方法及结果
- 尚未解决的问题

为事实记录来源。发现冲突时停止把该结论写成确定事实，先进入待确认流程。

### 3. 先规划主线，再撰写正文

大纲应形成因果或理解顺序，而不是照时间排列讨论过程。常用主线为：

```mermaid
flowchart LR
    A[为什么需要] --> B[要解决什么]
    B --> C[整体怎么做]
    C --> D[关键部分如何工作]
    D --> E[为什么这样选择]
    E --> F[何时适用及如何验证]
```

先为每一节写一句“本节要回答的问题”。如果相邻章节回答同一个问题，应合并；如果某节没有明确问题，应删除或重新定位。

### 4. 整篇综合写作

- 开头尽快建立问题、目标和核心结论，不复述产生文档的聊天过程。
- 正文只保留读者理解主题所需的内容。用户意见、评审 comment、修改过程、写作提醒和对话痕迹必须转化为已经确认的事实、方法或约束；无法转化时不写入正文。
- 使用自然段解释因果、机制和取舍；列表只用于并列项、步骤或检查项。
- 沿用用户使用且含义明确的术语。必须引入用户未提及的术语时，在首次出现处说明它在当前场景中的具体含义；缩写首次出现时写出全称。能用普通语言准确表达时，不额外创造术语。
- 让章节之间有承接关系，使读者知道为什么接下来要讨论该部分。
- 标题应直接命名业务对象、技术机制或读者任务，不照搬事实清单、评审模板或完整性检查中的词语。正文讨论数据清洗时，可按“字段标准化”“缺失值处理”“异常值识别”“重复数据合并”展开，而不是生硬套用“影响”“验收”“建议”等标题。
- 相同事实只在最合适的位置完整说明，其他章节通过引用或简短回指连接。
- 关系复杂时使用 Mermaid；数学关系使用 LaTeX。图应表达结构，文字应解释图中不明显的约束与结论。
- 来源集中放在文末“参考依据”，正文仅在证据边界会影响理解时说明来源类型。

### 5. 从读者视角复核

暂时忽略原始对话，只阅读成文结果并检查：

- 读者是否知道问题为何存在？
- 核心概念是否在首次出现时得到定义？
- 方案能否从整体进入细节，而不是突然罗列组件？
- 每个关键决定是否说明了原因和代价？
- 是否能判断方案适用于哪里、不适用于哪里？
- 是否给出了足以建立可信度的验证或依据？

## 写作风格

写作风格决定如何表达同一组事实，不决定文章讲什么。优先采用用户本次明确指定的风格；用户未指定且不同风格会明显改变结果时，可以请用户选择。目标和读者已经足够明确时直接判断，不为得到一个标签打断写作。

`writing_style` 支持以下类别：

- `technical`：面向工程师或技术决策者。使用准确术语，重点解释原理、数据结构、算法、接口、流程、异常处理和实现细节；示例应能帮助读者理解或落地。
- `explanatory`：面向跨职能或初次接触主题的读者。先解释概念和因果，再逐步引入术语，使用直观例子降低理解门槛。
- `research`：面向论文或技术研究阅读。背景和结论保持简洁，创新点、方法、实验设置和证据详细展开，区分论文事实与作者推断。
- `business`：面向产品、业务或管理读者。围绕场景、业务规则、角色协作、价值和决策信息组织，技术细节只保留到支撑判断所需的程度。
- `operational`：面向实际执行者。清楚说明前提、操作顺序、输入输出、判断条件、异常处理和可观察结果。
- `custom`：用户用 `style_notes` 给出自定义口吻、详略、术语密度、示例偏好或必须遵守的表达要求。

预设不是固定模板。`style_notes` 可以补充任意预设，例如“技术类，面向数据开发，重点写清 SQL 处理规则并给出输入输出样例”。选择 `custom` 时必须提供 `style_notes`。

无论采用哪种风格，都遵守以下边界：

- 以读者能顺畅理解为首要目标，不暴露“用户建议”“根据 comment 修改”“本次讨论认为”等协作过程。
- 不把写作动作写成知识内容，例如“这里需要说明”“建议补充示例”“后续可以展开”。
- 不为匹配风格而改变事实强度、虚构例子或省略会改变结论的条件。
- 章节结构从当前主题自然生长，不套用与主题无关的通用词汇。

## 文档类型

文档类型不是从零写作的目录模板，而是将交互内容整理成文时的取舍和叙述规则。各类型的成文主线、保留重点、删减内容和语言要求见 [document-type-styles.md](document-type-styles.md)。

支持的类型包括：方案型、分析型、需求型、架构说明、技术设计、项目指南、操作手册、接口文档、排障文档、故障复盘、决策记录、测试报告、调研对比、研究笔记、论文阅读、进展汇报、会议纪要和总结型。

同一文档类型仍可采用不同 `writing_style`。例如，同一份分析文档面向工程师时可以保留技术指标和计算细节，面向业务读者时可以降低术语密度，但两者都必须保留相同的数据口径和推理链。类型的整理规则不能被表达风格覆盖。

## 正文组织原则

### 完整不等于冗长

完整表示支撑理解和决策所需的信息闭环，不表示覆盖所有相关知识。每一段至少承担一种作用：定义问题、陈述结论、解释机制、提供证据、说明边界或连接上下文。

### 结论与论证配对

重要结论后应给出必要的机制、依据或取舍。避免只写“应当如此”，也避免先堆大量背景直到末尾才出现结论。

### 显式描述边界

至少说明适用范围、已知限制和例外。草稿中的未知信息应清楚标出；稳定文档不得保留占位内容。

### 控制元数据干扰

文档正文不重复展示每张日志的类型、证据等级和记录时间。日志 ID 保存在文档元数据中，来源集中放在文末。

### 消除协作过程痕迹

正式文档呈现已经整理好的知识，不呈现写作现场。将评审意见吸收进相应事实和方法，删除“有建议”“comment”“根据反馈调整”“本次沟通”等措辞。确实需要保留尚未解决的问题时，直接描述问题、已知条件和缺失信息，不描述是谁在什么对话中提出。

## 更新规则

更新正式文档不是在末尾追加“最新进展”。执行以下步骤：

1. 阅读全文和现有元数据。
2. 确定新事实影响哪些结论、章节、图示、示例和边界。
3. 更新事实已经改变的段落，删除失效或重复内容。
4. 重新检查章节顺序和过渡，必要时重组大纲。
5. 同步核查上下游描述能否继续成立。
6. 更新来源、关联日志 ID、摘要和日期。
7. 重新执行完整性检查；达不到稳定标准时将状态降为 `draft`。

文档保留当前有效认知，日志保留历史演进；不要在正文内维护重复的变更流水。

## 完整性检查

写入前逐项确认：

- [ ] 标题准确命名主题，摘要能独立说明文章价值。
- [ ] 目标读者、问题、目标和范围清楚。
- [ ] 核心结论在前部出现。
- [ ] 已按主要文档类型筛选和重排交互内容，没有把类型说明机械写成目录。
- [ ] 已采用用户指定的写作风格，或根据目标读者选择了合适风格。
- [ ] 用户未提及的术语已在首次出现时说明具体含义，缩写已给出全称，全文用法一致。
- [ ] 整体结构和关键机制得到充分解释。
- [ ] 关键选择包含理由、代价或候选方案比较。
- [ ] 边界、异常、限制和上下游影响没有遗漏。
- [ ] 示例、验证或证据足以支撑主要结论。
- [ ] 章节之间是逻辑递进，不是时间流水账。
- [ ] 列表没有代替本应展开的论证。
- [ ] 图、公式、正文和来源互不重复，各自承担清晰作用。
- [ ] `stable` 文档没有占位内容或伪装成事实的推断。
- [ ] 即使看不到原始对话，文章仍可独立理解。
- [ ] 章节名准确描述正文主题，没有机械使用“建议”“comment”“影响与验收”等协作或检查词汇。
- [ ] 正文没有用户意见、评审过程、写作提醒或其他对话痕迹。
- [ ] 项目已有主文档时，本次内容已优先合入主文档；若拆分，四项基础条件全部满足并记录了来源与理由。

## 常见失败模式

- 按对话发生顺序写“先做了什么，后来又做了什么”。
- 每张日志变成一个章节，重复“结论、依据、适用范围”。
- 只有标题和列表，没有解释机制、取舍和边界。
- 为追求完整加入与主题无关的百科背景。
- 新信息只追加到末尾，导致正文前后矛盾。
- 按功能、任务、阶段或日期不断创建新文档，导致项目事实散落和重复维护。
- 只因为文章较长就拆分，没有先删重、重组章节和改善导航。
- 拆分后主文档没有保留概览与入口，或主文档和拆分文档重复保存同一事实。
- 把推断润色成确定事实，或让文章语气强于实际证据。
- 正文反复展示时间、ID、证据标签，破坏连续阅读。
- 把“用户建议”“comment”“根据本次讨论修改”等协作过程当成正文内容。
- 套用通用检查清单，把“影响”“验收”“风险”等词机械变成章节，而没有按实际主题命名和组织内容。
- 把 `writing_style` 当作固定目录模板，导致不同主题写出相同结构。
