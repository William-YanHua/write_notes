# 项目知识双轨沉淀机制

> 说明项目如何用迭代日志保留结论演进，并默认持续维护同一份主文档形成系统知识。

## 背景与目标

项目交互会持续产生两类知识。一类是某次讨论中刚刚确认的决定、约束和验证结果，它需要保留发生时间、证据与后续变化；另一类是围绕项目形成的稳定认识，它需要让没有参与讨论的人也能理解背景、方案、取舍和边界。

如果所有内容都使用“结论—关键点—依据”的卡片展示，正式知识会变成条目清单；如果每出现一个新主题就创建一篇文章，项目事实又会散落、重复并逐渐不一致。反过来，如果只维护一篇没有历史依据的文章，决策证据容易在改写中丢失。因此，本项目采用日志与文档双轨沉淀：日志保存演进过程，正式文档默认维护一个稳定入口，表达项目当前的完整认识。

## 整体设计

```mermaid
flowchart LR
    A[对话、代码和验证结果] --> B{判断产物}
    B -->|独立增量结论| C[沟通与迭代日志]
    B -->|成熟系统认识| D[项目主文档]
    C -.事实和证据.-> D
    D --> E{是否形成独立维护边界}
    E -->|否| F[重组并更新主文档]
    E -->|是| G[拆分文档并保留主入口]
```

两条链路共享同一个项目边界和证据体系。项目根目录的 `.codex-knowledge.json` 以相对路径定位知识目录，使知识能够随仓库移动和版本管理。知识目录中的 `topics/` 保存卡片日志，`documents/` 默认保存一份项目主文档，`pending-review.md` 隔离冲突或证据不足的信息，`INDEX.md` 提供统一入口。

## 沟通与迭代日志

日志以一个中心结论为最小单位，适合记录已确认的技术选择、强约束、稳定事实、验证有效的方案、可复用踩坑和项目偏好。每张卡片具有稳定 ID，并保留结论、关键点、依据、适用范围、证据类型、时间和来源。

日志的价值在于可追溯，而不是连续阅读。新增信息与已有结论一致时更新原 ID；发生矛盾、范围不清或只能推断时，先进入待确认区，不静默覆盖旧结论。临时进度、完整聊天原文、秘密、偶发现象和容易从代码直接获得的细节不进入日志。

## 项目主文档

第一份正式文档作为项目主文档，围绕项目整体持续维护。创建前先确定目标读者、阅读目标、范围和非目标，再从日志、代码、配置、测试结果和正式资料中建立事实清单。文章按照理解和因果顺序组织，通常先说明问题与目标，再解释整体方案、关键机制、设计取舍、适用边界和验证结果。

新功能、新任务、新阶段、新主题和新日期都先进入这份主文档。更新时不是在末尾追加进展，而是阅读全文后修改或重组相关章节，并同步修正概览、关系、边界、图示、示例和验证信息。文档 ID 与路径保持稳定，使读者始终可以从同一个入口理解项目。

日志卡片可以为文档提供事实和证据，但一张卡片不等于一个章节。正文不会重复展示每条日志的时间、类型和证据标签，而是综合相关事实形成自然段、关系图和必要的例子；引用过的日志 ID 保存在文档元数据中，其他依据集中列在文末。

## 必要时拆分

拆分是例外，而不是按主题自动分文件。只有内容形成稳定且可独立命名的边界，需要长期独立维护、阅读或评审，并且主文档经过删重、重组和改善导航后仍难以维护时，才考虑拆分。拆分前还必须能用一句话分别说明两份文档的职责，避免重复保存同一组核心事实。

合理信号包括不同维护者或发布节奏、明显不同的读者和独立交付要求，以及需要长期单独保存的事故复盘、研究报告或规范。单纯出现新模块、新版本、里程碑或较长正文并不构成理由。确需拆分时，新文档记录来源主文档和具体理由；主文档仍保留必要概览、适用边界和链接，保证项目全貌只有一个首要入口。

## 写入与更新规则

一次任务只产生零散事实时，仅写日志。材料已经能补充系统认识，或用户明确要求撰写文档时，先扫描 `INDEX.md` 与 `documents/`；只要已有主文档，就优先整体更新它。重要设计、实现和排障同时产生两类价值时，先固化日志，再以确认后的事实更新主文档。

写入脚本在项目已有正式文档后默认拒绝再次新增。只有输入同时声明有效的来源文档和具体拆分理由时，脚本才允许创建拆分文档。更新拆分文档时保留既有来源关系，避免文档在后续迭代中失去归属。

## 完整性与证据边界

正式文档至少要形成三个有实质内容的章节，并能在脱离原始对话后独立理解。完整性不等于篇幅长，而是问题、目标、方案、机制、取舍、边界和验证形成信息闭环。列表只表达并列项或步骤，不能代替本应展开的解释和论证。关系复杂时使用 Mermaid，数学关系使用可渲染的 LaTeX。

两条链路都只采用用户确认、执行验证或项目材料直接支持的事实。推断不会因为写进文章而自动变成结论。信息尚不完整但已有持续价值时，文档标记为草稿；只有正文完整、关键事实明确且没有占位内容时，才标记为稳定。

## 适用边界

这套机制服务于当前项目中未来仍会复用的知识，不建设跨项目集中知识库，也不替代代码、接口定义、测试、版本历史或专门的运维系统。能够由编译器、测试或自动化稳定保证的事实，应优先留在对应系统中；知识文档只补充这些系统难以表达的原因、关系、取舍和使用边界。
